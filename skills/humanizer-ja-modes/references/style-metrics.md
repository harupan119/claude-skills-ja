# 表記・文体の定量基準（全モード共通の下地）

AI 臭の検出（SKILL.md の第1〜3層）とは別に、**人間が書いた文章でも直すべき表記・文体の崩れ**をここにまとめる。AI 臭を抜いた後の文章がこの基準を外れていると、機械的に書き換えた痕跡が残っていることが多い。

機械的な点検は `scripts/ja_style_check.py` で行う。

```bash
python3 scripts/ja_style_check.py report.md --mode academic
python3 scripts/ja_style_check.py es.md --mode business --max-len 90

# 慣用句の誤用辞書（40項目）も当てる。リポジトリを丸ごと置いている場合のみ
python3 scripts/ja_style_check.py report.md --prh ../../sources/mirror/textlint-rule-ja-no-abusage/dict/prh.yml
```

## 出典と、この表の位置づけ

基準値と規則は、textlint-ja のルール群と、その元になった『JTF日本語標準スタイルガイド（翻訳用）』から取った。原本はリポジトリの `sources/mirror/` にコミット固定で複製してあり、各行の「出典」列はそのディレクトリ名を指す。

- textlint-ja の既定値は**技術文書向けで、やや厳しめ**に設定されている（同プリセットの README 自身がそう明記している）。レポート・論文にもそのまま使えるが、提出先の規約が別の値を定めていれば規約が優先する。
- JTF のガイドは翻訳用の表記規則である。記号・数字・スペースの規則は和文一般に通用するため採った。敬体か常体かは「目的に応じてどちらかに統一」とだけ定めており、どちらを選ぶかは本スキルのモード判定で決める。

## 文の長さと区切り

| 基準 | 既定値 | 検査 ID | 出典 |
|---|---|---|---|
| 1文の長さ | 100字以下（厳しめなら90字） | `sentence-length` | textlint-rule-preset-ja-technical-writing |
| 1文の読点 | 3個まで | `max-ten` | 同上 |
| 漢字の連続 | 6字まで。固有名詞は `--allow-kanji` で例外にする | `kanji-run` | 同上 |
| 逆接の「が、」 | 1文に1回まで | `doubled-ga` | 同上 |
| 同じ接続詞 | 連続する文の頭で繰り返さない | `doubled-conjunction` | 同上 |
| 同じ助詞 | 1文の中で同じ助詞を繰り返さない（例：「材料不足で代替素材で」）| 未実装。形態素解析が要るので textlint 本体に任せる | textlint-rule-no-doubled-joshi |

文長と読点は連動する。100字を超える文はほぼ必ず読点が4つ以上ある。分けるときは、読点で切るのではなく**主張の単位**で切る。1文に主張が2つ入っているから長くなっている。

漢字の連続は、AI 臭の第2層12（漢語の過剰連続）を数値で捉えたものに当たる。「情報処理技術者試験制度」のような固有名詞・法令名・制度名は、言い換えられないので例外に登録する。

## 文体の統一

| 基準 | 検査 ID | 出典 |
|---|---|---|
| 本文は敬体（ですます）か常体（である）のどちらかに統一する | `mixed-style` | textlint-rule-preset-JTF-style（JTF 1.1.1）|
| 見出しは常体か体言止め | 目視 | JTF 1.1.2 |
| 箇条書き・図表のキャプションは本文の文体に合わせる | 目視 | JTF 1.1.3 / 1.1.5 |

academic は常体、business は敬体を正として、少数派の文末を報告する。casual は多数派を正とする。**図表のキャプションと図中の文字も本文の文体に揃える**。本文だけ常体に直して、キャプションに「〜を示しています」が残る例が多い。

## 語句（冗長・弱い・二重否定・誤用）

| 型 | 例 → 直し方 | 検査 ID | 出典 |
|---|---|---|---|
| 冗長 | することができる → できる／することが可能 → できる | `redundant` | textlint-rule-ja-no-redundant-expression |
| 冗長 | であると言える → である／であると考えている → どちらかに絞る | `redundant` | 同上 |
| 冗長 | 確認を行う → 確認する（「処理を行う」とカタカナ語・英字の目的語は除外）| `redundant` | 同上 |
| 弱い表現 | かもしれない／かも。 | `weak-phrase` | textlint-rule-ja-no-weak-phrase |
| 二重否定 | ないわけではない／ないとは限らない／ないとは言い切れない／ないことはない／ないものではない／なくはない／ないでもない | `double-negative` | textlint-rule-no-double-negative-ja |
| 誤用 | 読みずらい → 読みづらい／可変する → 可変の・変えられる／適応する（規則を）→ 適用する | `misuse` | textlint-rule-ja-no-abusage |
| ら抜き | 見れる → 見られる／来れる → 来られる | `ra-nuki` | textlint-rule-no-dropping-the-ra |

弱い表現は academic の「適正ヘッジ」（modes/academic/MODE.md）と衝突しない。適正ヘッジは「〜の可能性がある」「〜と関連していた」のように**根拠の強さを示す**言い方で、「かもしれない」は根拠の強さを示さずに主張を弱めるだけである。academic では前者に置き換える。

二重否定は、否定並列構文（第2層23）と同じく、立場を明示しないための言い方として AI 文に出やすい。肯定文に直すか、条件を明示する（「ないとは限らない」→「〜の場合には〜する」）。

`ra-nuki` は代表的な動詞だけを辞書で見ており網羅的ではない。`misuse` の「適応／適用」は文脈判断が要るため機械検査に入れていない。

## 記号・数字・スペース

| 規則 | 検査 ID | 出典（JTF 項番）|
|---|---|---|
| ダッシュ（—―–）は和文で原則使わない | `dash` | 4.2.9 |
| ハイフン・セミコロンは和文で原則使わない | 目視 | 4.2.6 / 4.2.8 |
| コロン・感嘆符・疑問符は和文で多用しない | `exclamation`（casual 以外）| 4.2.7 / 4.2.1 / 4.2.2 |
| 句読点は全角の「、」「。」 | 目視 | 1.2.1 |
| 全角文字と半角文字の間、全角文字どうしの間にスペースを入れない | 目視 | 3.1.1 / 3.1.2 |
| 句点の直後に半角空白を残さない | `space-after-kuten` | 本スキル独自（太字除去の後始末）|
| 数えられるものは算用数字、慣用句は漢数字（「3回」「一度に」）| 目視 | 2.2.2 |
| 「〜か月」「〜か所」と書く（「ヵ月」「ヶ所」にしない）| `misuse` | 2.2.3 |
| 算用数字・アルファベットは半角 | 目視 | 2.1.8 / 2.1.9 |

ダッシュの禁止は SKILL.md の第1層5と同じ結論になる。第1層5は「AI の書式マーカーだから」、JTF は「和文の表記規則として使わない」という別々の理由で、どちらから見ても残す理由が無い。

全角と半角の間のスペース（3.1.1）は、Markdown で書く技術文書では空ける流儀もある。提出物に JTF の規則を当てるかどうかは提出先に合わせ、**文書内で統一されていること**を優先する。

## 使い方の注意

- 出力は「読み直す箇所の候補」であり、全件を機械的に直すものではない。とくに `kanji-run` は固有名詞で、`sentence-length` は定義文や引用で、正当に基準を超える。
- 「」の中は引用や語の言及とみなし、語句系の検査（冗長・弱い・二重否定・誤用・ら抜き）から外している。逆に、括弧なしで語に言及した箇所は拾ってしまう。
- コードフェンス・表・インラインコード・URL は検査しない。

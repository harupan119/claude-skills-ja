# calendar-scheduling — 空き時間を出して予定を重複なく入れる

## いつ使うか

- 日程候補をメールや返信文に入れるとき
- ユーザーの空き時間を確認するとき
- 表・画像・メールの日程を **カレンダーに登録する** とき → 「予定を登録するとき」へ

## 手順（空き時間の提示）

### Step 1: 全カレンダーを取得する

**必ず `list_calendars` から始める。** Inboxだけ見ない。

```
list_calendars() → 全カレンダーIDを取得
```

よくあるカレンダー：バイト、大学、Inbox、日本の祝日、タスク

### Step 2: 全カレンダーのイベントを並行取得する

対象期間の全カレンダーを **同時に** 取得する。

```
list_events(calendarId=バイトID, ...)
list_events(calendarId=大学ID, ...)
list_events(calendarId=InboxID, ...)
```

### Step 3: 曜日はコードで出す（暗算しない）

**日付から曜日を導く計算を、頭の中でやらない。** 同梱の `scripts/calendar_calc.py` か、手元の `python3` / `date` で出す。

```bash
python3 scripts/calendar_calc.py weekday 2026-07-28 2026-07-29
# 2026-07-28（火）
# 2026-07-29（水）
```

コード実行が使えない環境に限り、年の基準日（例：2026-01-01 = 木曜）から数え、そのことを回答に明記する。

提示する日付には必ず曜日を併記する。「自分で検算した」は検算にならない。検算とは、上のコマンドの出力と照合することを指す。

### Step 4: ブロック時間を整理する（件数が多いときは `free` に渡す）

取得したイベントをリスト化：
- 日付・曜日・開始〜終了時刻・イベント名・カテゴリ（バイト/サークル/大学等）

### Step 5: バッファルールを適用する

**各予定の開始1時間前から終了まではブロック。**

例：
- バイト 16:00〜 → 15:00以降はNG
- サークル 19:00〜 → 18:00以降はNG
- 1時間のミーティングなら、終了時刻がバッファ開始以前になるよう逆算

### Step 6: 空きスロットを列挙する

予定が数件なら目で引いてもよいが、**複数カレンダー・複数日にまたがるなら、区間の引き算はコードでやる。** `list_events` の `items` をそのまま `events` に並べた JSON を作り、`free` に渡す。

```bash
python3 scripts/calendar_calc.py free busy.json
# 10/1（木） 11:30〜15:00（3h30m） / 21:00〜22:00（1h00m）
# 10/2（金） 09:00〜18:00（9h00m）
# 10/3（土） 09:00〜22:00（13h00m）  ※終日: 合宿
```

`free` がやっていること：

- `dateTime` を指定したオフセット（既定 `+09:00`）にそろえる。`Z` 付きの UTC で返ってくる予定も正しく換算する
- 各予定の開始 `buffer_before_minutes`（既定60分）前から終了までを塞ぐ（Step 5 のバッファ規則）
- 終日予定は `end.date` が**翌日（排他的）**である点を踏まえて日付範囲を解釈する。既定では塞がずに注記だけ出す。祝日カレンダーまで塞いでしまわないためで、塞ぎたいときは `"all_day": "block"`
- `status: cancelled` の予定は除く

出力をそのまま候補として貼らず、Step 4 の一覧と見比べて、塞ぐべきでない予定（例：自分が「空き時間」として入れているもの）が混ざっていないかを確認する。

```
例：
- 4/23（木）19:00〜 ✓
- 4/29（水）17:00〜 ✓（サークル19:00のため18:00終了まで）
```

## 予定を登録するとき

読み取りと違い、書き込みは失敗が「重複」として残る。登録前に必ず Step A〜D を通す。

### Step A: 曜日から年を確定する

表や画像の日付には曜日が併記されていることが多い。`7/28(火)` の曜日が一致する年に登録する。年はコードで確定し、確定した年を本文に書く。

```bash
python3 scripts/calendar_calc.py year 7/28 火 --from 2024 --to 2030
# 2026-07-28（火）
```

複数の年が当たる場合（曜日は概ね5〜11年周期で一致する）は、近い年を選ぶ前にユーザーに確認する。表の中に曜日が合わない日付が1つでもあれば、表の誤記か年の取り違えなので、登録前に指摘する。

### Step B: 重複チェックは「時間枠」で行う（名前検索に頼らない）

**`q=` のキーワード検索だけで重複を判定してはいけない。** 同じ予定が複数の表記で入っている。

実際に踏んだ表記ゆれの型（名前は伏せて構造だけ示す）：

| 実体 | 登録されている表記 |
|---|---|
| 定例の練習 | `Orchestra` / `orchestra `（末尾スペース）/ `オーケストラ` |
| 関連する別予定 | `Orchestra合宿` / `Orchestra-打ち上げ` |

`q=Orchestra` で検索するとカタカナ表記が漏れ、同じ枠に2件作ってしまう。**英字とカタカナ、大文字小文字、末尾スペースの4方向にずれる**と考えておく。

正しい手順：**タイトル無指定**で対象期間を全カレンダー分取得し、開始時刻が一致する予定を照合する。

```
list_events(calendarId=各ID, timeMin=期間開始, timeMax=期間終了,
            singleEvents=true, orderBy=startTime)
→ 登録したい各枠と同じ開始時刻の既存予定がないか目で確認
```

### Step C: 表記・場所・登録先を既存に合わせる

過去の同種予定を1件読んで、タイトル表記／場所欄の使い方／登録先カレンダーを踏襲する。

- 定例のサークル活動 → primary カレンダー、タイトルは英字表記で統一、場所欄に会場名
- アルバイト → 専用カレンダー

### Step D: 全件を表で提示して承認を取ってから書く

作成する予定を「日時・場所」の表にして提示し、承認を得てから実行する。過去日を含めるかもここで確認する。削除・上書きも同様に承認を取る。

### 重複が見つかった場合

どちらを残すかはユーザーに選ばせる。残す側が決まったら、削除後に期間を再取得して各枠1件になったことを確認し、その出力を報告に含める。

## なぜ暗算を禁じるのか（根拠文献）

日付計算と予定調整は、LLM が「だいたい合っているが最後で1ずれる」種類の誤りを出しやすい領域として、繰り返し測定されている。

- **日数計算は1日ずれる。** Test of Time（Fatemi et al. 2024, arXiv:2406.09170）の時間算術課題で、2日付間の期間を問う Duration の正答率は、評価した3モデル（Claude-3-Sonnet / GPT-4 / Gemini 1.5 Pro）で13.5〜16.0% だった。誤答で最も多かったのは正解からちょうど1日ずれた答えで、うるう年の扱いと、過去へ遡る向きの計算も典型的な誤りとして挙げられている。空き時間探しに相当する Schedule も29.6〜43.6% にとどまる
- **曜日は、よく知られた日付を外れると崩れる。** Lost in Time（Saxena et al. 2025, arXiv:2502.05092）は年間カレンダーの画像を読ませて曜日を問う課題で、クリスマスのような有名な日付は当てても、「その年の153日目は何曜日か」のような加算を要する問いで正答率が大きく落ちることを示した。表や画像から予定を登録する場面（Step A）がちょうどこれに当たる
- **予定調整は、情報が全部与えられていても半分以上外す。** NATURAL PLAN（Zheng et al. 2024, arXiv:2406.04520）の Calendar Scheduling は、Google Calendar 相当の予定をすべて文脈に入れた状態でも最高48.9%（Gemini 1.5 Pro）だった
- **自分で見直させても直らない。** 同じ NATURAL PLAN の旅程計画課題で「誤りがないか確認して直せ」と自己修正させると、全モデルで正答率が下がり、強いモデルほど下げ幅が大きかった。外部からのフィードバックなしの自己修正が推論課題で改善しないことは Huang et al. 2024（arXiv:2310.01798）も報告している
- **計算をインタプリタに渡すと当たる。** PAL（Gao et al. 2023, arXiv:2211.10435）は、問題の分解だけをモデルにやらせ、計算を Python に任せる方式で、日付理解課題（BIG-Bench Hard の Date Understanding）の正答率を連鎖思考より絶対値で11.4ポイント上げた

したがってこのスキルでは、曜日・年・空き時間の3つをコードで出し、モデルの役割を「何を計算するかを決め、結果を読んで提示する」に限定している。

数値は各論文の測定時点のモデルでの値で、現行モデルでは改善している可能性がある。ただし、誤りの型（1日ずれ・うるう年・自己修正の無効）がコード実行で消えるという構造は、モデルの世代に依存しない。
